# Lorvex 1.0.0 (178)

**Lorvex's MCP helper now handles the protocol itself, and assistants that
support MCP 2026-07-28 use that version with Lorvex.** Until this build the
official Swift SDK's server carried every message between an assistant and
Lorvex's 122 tools. The helper now owns the stdio transport, the JSON-RPC
framing and the method dispatch, and keeps the SDK for its data types. It
serves both the `initialize` handshake that Codex and older clients use and
the 2026-07-28 protocol, in which each request carries its own version and
the client's capabilities and a client starts with `server/discover`. Claude
Code 2.1.331 now uses 2026-07-28 with Lorvex; Codex 0.170.0 keeps
`initialize` with 2025-06-18. The setup is unchanged.
[`docs/decisions/mcp-protocol-layer.md`](../decisions/mcp-protocol-layer.md)
records the design, and why moving the helper to the Rust SDK was rejected.

What a tester can notice:

- **A task title written like a web data address** (`data:,hello`) is saved
  as typed. The SDK decoded such a string as binary data, so `create_task`
  rejected the title as empty, and a stored title of that shape came back
  base64-encoded.
- **Listing the tools is faster.** `tools/list` takes 3.4 ms instead of
  80 ms and `get_overview` 2.2 ms instead of 7 ms; `initialize` answers
  22.3 ms after launch, as before (22 ms). Each is the median of 20
  launches after a first one, release build of the helper over a temporary
  database on the owner's Mac.

Nothing changes on iPhone and iPad; the iOS build is built from the same
commit and carries the same number.

For the project rather than testers:

- **The filter added in build 177 for Codex's capabilities is gone.** The
  helper reads only the client fields it uses, so an unfamiliar capability
  value can no longer stop a connection, and `ClientCapabilityTolerantTransport`
  was removed with it.
- **Two responsiveness traces are recorded** in `ROADMAP.md`, with the
  recording recipe in `VERIFICATION.md`. A tab switch on iPhone costs 80 to
  100 ms of main-thread time whatever the tab holds, almost all of it UIKit,
  SwiftUI and Core Animation moving the tab's views. Today's fling over the
  stress content spends 445 of the main thread's 1,314 ms preparing cells
  that scroll in, and no app function passes 12 ms.

## Verification

The full suites passed on the tree before the review corrections described
below. The app package ran 5,295 Swift Testing tests and 666 XCTest tests,
2 of them skipped; the core package ran 225 and 14. Counted as build 177's
record counts them, that is 5,520 Swift Testing tests and 680 XCTest tests.
Every static gate passed.

After the review corrections, the MCP host's own tests passed (57 tests in
6 suites: the protocol, the host over the real tool registry, the stdio
channel, idempotency and the daily-backup tools), as did the stdio smoke
check, its 10 unit tests and every static gate. The smoke check runs the
built development helper over a temporary database: `server/discover`,
`tools/list` and `get_overview` with 2026-07-28 metadata over Unix socket
pairs, the way Claude Code and Claude Desktop launch it, then the
`initialize` flow over pipes, the way Codex does, including a task titled
`data:,…`. The build number change passed the app metadata tests.

Each real client ran one headless session against the development helper
over a temporary database, before the review corrections. Claude Code
2.1.331 probed with `server/discover`, logged `protocolEra: "modern"` and
`negotiatedProtocolVersion: "2026-07-28"`, listed 122 tools and called
`get_overview`. Codex 0.170.0 (`codex exec`) sent `initialize` with
2025-06-18 and its experimental capabilities and called `get_overview`.
Claude Desktop and Codex Desktop were not tried; the tester notes ask for
both.

Two independent reviews read the change before it was committed. Each got
the diff and a description of its intent, not the author's conclusions.

- **Concurrency and I/O.** Found one defect: the stdin reader never released
  the lines it had delivered, because `Data.removeFirst` moves the start
  index and keeps the storage. The reviewer measured 103.6 MB held after
  100 MB of input. The reader now copies the unfinished line, and a test
  checks that it holds no more than that line; against the old code the
  test fails, holding all 1,600,000 bytes it was fed. The review also found
  that the cancellation test did not prove the tool was cancelled, that one
  write test blocked a thread of Swift's shared pool, and that the decision
  record called the descriptors blocking. All are fixed. It suggested
  treating `SIGINT` like the end of input; that was not done, and the
  decision record says why.
- **Protocol correctness.** Found nothing that stops a client. Three
  departures from the specification were fixed: an error whose request id
  could not be read now leaves `id` out, as MCP's schema has it, instead of
  writing `null`; a request whose metadata holds 2026-07-28 client fields
  but no version now gets -32602; and the decision record no longer says
  2026-07-28 has `ping`, which Lorvex still answers there. Three were left,
  with reasons recorded: an unknown tool name still returns an error result
  the model can read rather than a protocol error, as before this build;
  `progressToken` is not passed on to tools, none of which reads it; and a
  request inside a batch cannot be cancelled, which only protocol 2025-03-26
  allows and the specification permits. Two gaps it found in the tests are
  now covered: falling back to `initialize` after a refused probe, and
  reusing an id after a cancellation.

The built metadata was read in what shipped. The iOS package and the Mac
App Store package each carry build 178 and hold 89 actions, every one with
a declared lock policy, as in build 177.

The hosted check on the build commit, a second run from a clean checkout on
a machine set to UTC, was started before the build was archived (GitHub
Actions run 45384305347, 03:27 PST); the upload does not wait for it. It is
still running as this record is written; its result is added when it
finishes.
