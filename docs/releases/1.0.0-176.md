# Lorvex 1.0.0 (176)

**Lorvex keeps a copy of your data from each day, so a deletion is no
longer final.** Until this build, a task, list, habit or memory entry that
was deleted, or a note an assistant overwrote, was gone once undo could no
longer reach it. The Mac and iOS apps now save one full copy a day on the
device and keep it for up to four weeks.

- **What is kept.** Each copy is the same ZIP that Export writes. Lorvex
  keeps the 7 newest days and, before those, the earliest copy of each of
  the 4 weeks before. A day with an empty store is skipped, so emptying the
  app cannot push the good copies out.
- **When.** The app saves the day's copy the first time it refreshes on
  that day: at launch, when it comes to the front, after a change, and on
  the Mac at the start of each day while it stays open. The day is Lorvex's
  day, in the time zone set in Lorvex. A failed copy is logged under
  `daily_backup` and tried again 30 minutes later.
- **Where.** In a `DailyBackups` folder beside the database. It is excluded
  from iCloud Backup and Time Machine, it is never synced, and erasing the
  device's data deletes it.
- **Settings.** "Daily Backups", after Import, shows the latest copy. On
  the Mac, Show in Finder opens it; on iPhone and iPad the row opens every
  copy, each with a share button. Turning off Keep Daily Backups asks first
  and then deletes every copy. The switch belongs to the device: it is not
  synced, and an assistant can read it but not change it.

For an assistant connected through MCP:

- `list_daily_backups` lists the Mac's copies with their day, the time each
  was written and its size.
- `compare_with_daily_backup` compares the current data with one copy and
  returns, per category, what the copy has that is gone now (in full, so it
  can be created again), what was added since, and the fields that differ.
  A changed checklist, reminder list or habit history shows only the
  entries that differ, and a change of timestamps alone is not a change.
  Every user-written field is fenced. A removed item comes back under a new
  id: `create_task` refuses the `original_id` of a deleted task.

Also in this build, from an accessibility audit of the iPhone screens:

- **Complete buttons you can read.** A white label on the system green
  measured 2.2:1 in light and 2.0:1 in dark. The habit's Complete Today and
  the task pane's Complete now use a deeper green of the same hue, 4.7:1
  under white.
- **The weekly journal's filter** was an 18-point-high target. It now
  reaches 14 points above and below its label; the layout is unchanged.
- **Today's next event** read "In 160 minutes". It now reads "In 2 hr 40
  min", with the units spelled out for VoiceOver, in all 30 languages.

## Verification

The full suites passed on the daily backups tree with the machine in the
Pacific time zone. The app package ran 5,490 Swift Testing tests and 677
XCTest tests, 2 of them skipped. The core package ran 2,636 XCTest tests, 24
of them skipped (23 are benchmarks that run on request), and 1 Swift
Testing test. Every static gate passed, as did the check of localized
string arguments against the catalog. One change came after the full run:
the Mac's Show in Finder button is hidden, not disabled, while no copy
exists. The Mac app built with it; no test covers that view.

The backup tests run against a store on disk. They cover the keep rule
over 120 consecutive days, an erase that lands while a copy is being
prepared, turning backups off and a pass that finds them off with copies
still on disk, unfinished and far-future files, the 30-minute wait after a
failure, and a pass the person asks for, which skips that wait. The MCP
tests cover fencing of every user-written field in a comparison, including
checklist text, a tag's name and a memory key; a checklist step toggled
and toggled back, which is not a change; narrowing by category, id and
limit; and the arguments the tools refuse.

The development build of the MCP host lists 122 tools; the `tools/list`
result is 165,447 bytes of compact JSON, up from 165,355 before the two
descriptions were reworded (both measured on 2026-11-23).

Two independent reviews read the change before it was committed. Each got
the diff and a description of its intent, not the author's conclusions.

- **Core and MCP.** Found no fault in the keep rule, the erase handling,
  sync privacy or fencing. It found nine smaller faults, all fixed: a
  switch turned off during a pass could leave a copy behind; on iOS the
  storage lock was held for the whole write; a timestamp inside a
  checklist step counted as a change; `backup_taken_at` was never set;
  `linkedTaskIDs` came out as `linked_task_i_ds`; an empty `entities` list
  was accepted; the privacy text said copies never leave the device, when
  sharing one or an assistant reading one does; a copy dated in the future
  was kept; and the pass that turning backups on starts could be held back
  by the failure wait.
- **Settings and documents.** Found that the turn-off dialog had no
  Cancel, the section went stale after an erase, a failed turn-off hid the
  copies, an error showed raw text, the switch flickered, the iPhone footer
  pointed to an assistant the iPhone cannot connect, the privacy text said
  "five weeks", and the tool count was stale in the documents and in the
  lists the static gates compare. All are corrected. Left as they are: the orange error text uses the app's
  existing warning color, and a failed first copy after turning backups on
  shows "None yet" with the failure in the diagnostics log.

A test written for the corrections showed that a deleted task cannot be
re-created at its old id: `create_task` refuses the `original_id` of a
deleted task. The tool description says a removed item comes back under a
new id.

The iPhone Settings section and the list of copies were captured in light
and dark after the review's corrections. The Mac Data tab was captured in
light before them and in dark after them. The first iPhone capture
showed the copy a day early: `Text(date, format:)` formats in the
environment's time zone, and the day is stored as UTC midnight. The label
now formats the UTC day; the later captures show the right day.

Not exercised by automation:

- A copy on a real device across a day boundary. The tests pass the day
  in; no run waited for midnight.
- iOS suspending the app during a copy. The publish registers with the
  suspension guard like every store operation, and no test suspends it.
- Sharing a copy from the iPhone list. The capture shows the button; the
  share sheet was not opened.
- A real assistant client calling the two tools. They ran in tests and
  through a command-line wrapper around the development host.

The built metadata was read in what shipped. The iOS package and the Mac
App Store package each carry build 176 and hold 89 actions, every one with
a declared lock policy, as in build 175.

The hosted check on the build commit, a second run from a clean checkout
on a machine set to UTC, was started before the build was archived (GitHub
Actions run 45250314539); the upload does not wait for it.
