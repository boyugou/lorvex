# Lorvex 1.0.0 (175)

**Today follows one rule: a task's day is the day it is planned for, or the
day it is due when it has no plan.** Today holds every unfinished task whose
day is today or earlier, and every task that has been started. Three faults
came from code that worked out a task's day in its own way, and this build
removes them.

- **A task moved to a later day leaves Today.** A task whose due date had
  passed stayed on Today whatever day it was planned for, so moving it to
  Friday changed nothing on the screen. It now leaves Today, keeps its red
  due date, is upcoming on Friday, and returns to Today that day. A started
  task stayed on Today whatever its dates. Moving one to a later day now
  pauses it in the same step, so the move always takes the task off Today.
  Changing the planned date alone leaves a started task started.
- **A repeat starts on the planned day.** Turning on a repeat for a task
  with no due date started the series today, whatever day the task was
  planned for: "every three days from Thursday" counted from the day it was
  typed. The series now starts on the planned day when that is today or
  later, otherwise today, and that day becomes the task's due date. The
  repeat editors on Mac, iPhone and iPad preselect that day's weekday. A
  planned day that has passed moves to the start day. Each later occurrence
  keeps its distance from the plan, so a plan left in the past put every
  later occurrence on Today the moment the one before it was completed.
- **Suggested times for another day hold that day's tasks.** An assistant
  or the Shortcuts action can ask for suggested times for a day other than
  today; the apps ask for today only. Such a suggestion was built from
  Today's list as of that day, so asking for Wednesday placed Monday's
  unfinished work and left Wednesday's own task out. It now holds the open
  tasks planned for that day or, with no plan, due on it. A started task is
  on Today only.

Also in this build:

- **Turning a repeat off never cancels a finished occurrence.** Turning the
  repeat off on an occurrence, or cancelling it with its series, withdraws
  the occurrences generated after it. A completed one among them became a
  cancelled one and lost its completion time; the build 174 record lists
  this as found after that build was cut. The step is now refused when it
  would withdraw a completed occurrence, and the message names the way that
  works: turn the repeat off on the series' latest occurrence, which
  withdraws nothing. The sentence is in all 30 languages.
- **Time zone names outside Apple's list.** A device can report its zone
  under a name Apple's list of identifiers leaves out, such as
  `Asia/Kolkata` or `US/Pacific`. On such a device setup failed, and with no
  stored time zone every read that needs today failed with it. A name given
  on the device now resolves to the listed identifier of the same zone, and
  that identifier is what syncs. Abbreviations (`PST`) and fixed offsets
  (`GMT+5`) are still refused.
- **iPhone date editor.** Turning on a due, planned or available-from date
  in the iPhone edit sheet started the picker on the phone's calendar day.
  It now starts on Lorvex's today, which is another day when Lorvex's time
  zone is not the phone's.

For an assistant connected through MCP:

- **Results in both parts.** Every tool result held a one-line summary as
  text and its data only as structured content, and clients differ in which
  part they hand their model. A client that forwards only text gave its
  model no data. A client that forwards only structured content never
  showed the note about arguments a tool ignored. The text now ends with
  the same data as JSON, which the MCP specification asks of a tool that
  returns structured content, and the note is the data's `warnings` field.
- **Reminder times on the user's clock.** A reminder time can be written as
  a date and time with no offset (`2026-12-01T10:00`) and is read in the
  user's time zone. An instant with `Z` or an offset is accepted as before.
  A time the clocks skip is refused; a time that occurs twice is the earlier
  one. A reminder in a result carries `local_time` and `timezone` beside the
  UTC instant once the user's time zone is set.
- **Deferring.** `defer_task` and `batch_defer_tasks` refuse a day that is
  not after today and point to `update_task`.
- **Smaller reads.** `get_session_context` returns the date, weekday, local
  time, time zone and working hours. `get_upcoming_tasks` starts tomorrow
  and lists task ids per day instead of repeating every row.
  `get_overview` with `shape` `full` leaves out empty fields and returns the
  ten most important tasks that are not on today.
- `search_calendar_events` reports the number of matches on a last page,
  including zero for a search that matched nothing, which used to read as
  unknown. The descriptions of `set_task_recurrence`,
  `propose_daily_schedule`, `batch_update_tasks` and `get_dependency_graph`
  state where a series starts, which tasks a day holds, which tool moves
  tasks between lists, and which way a dependency edge points.

## Verification

The full suites passed on the tree of the commit before the build number
changed, with the machine's time zone set to Asia/Tokyo. The app package ran
5,483 Swift Testing tests and 665 XCTest tests, 2 of them skipped. The core
package ran 2,636 XCTest tests, 24 of them skipped (23 are benchmarks that
run on request), and 1 Swift Testing test. A full run in
America/Los_Angeles passed before the last review's corrections, and the
suites those corrections touch passed there afterwards. Every static gate
passed. The hosted run on the build commit, a second check from a clean
checkout on a machine set to UTC, had not finished when the build was
released; the upload does not wait for it.

Until this build the suites passed only with the machine in the Pacific
time zone. Four commits corrected tests and a preview seed that built a day
from the machine's midnight. The time zone name fault and the iPhone date
editor's default were found in that work.

An assistant carried out seven whole requests against a seeded store of 44
tasks, twice: once before the Today rule changed and once after. The
requests were to plan a day, clear an inbox, move a day's work because of an
absence, describe the week, capture three things, pick up handed-over
tasks, and report finished work. Each ran in its own copy of the store
through the development build of the MCP host, and each reply was read
against the store's final state and the log of calls. The first run found
the Today fault: the assistant deferred four overdue tasks and reported
them gone from Today, and they were still there. The second run found what
the build's last commit changes: reminder times an assistant had to convert
to UTC itself, the repeat that started on the wrong day, and another day's
suggestion built from Today's list. That commit's changes were then covered
by tests and not run by an assistant again.

Every request was carried out in both runs. The first took 69 tool calls,
none of which failed, and 241,014 bytes of tool results. The second took 89
calls, 1 of which failed, and 199,861 bytes. Read directly on the same
store, `get_overview` with `shape` `full` went from 17,725 to 9,376 bytes
and `get_upcoming_tasks` for seven days from 10,416 to 5,603. Each request
ran once per run, so the totals show a direction and are not a controlled
comparison. What the runs leave open is in the
[roadmap](../../ROADMAP.md).

Six independent reviews read these changes before they were committed. Each
got the diff and a description of its intent, not the author's conclusions.

- **Ending a series.** Found that Siri's delete reported the wrong reason,
  advice that named a "current" occurrence a finished series does not have,
  two overstated sentences in the documents, and a test state built by hand
  that the app reaches through its own writes. All are corrected.
- **Dates written as days.** Read about 40 places that write a due,
  planned, available-from or deferral day. None was wrong in shipping code.
  It found the preview seed that built days from the machine's midnight and
  the iPhone edit sheet's default day, both corrected. Left as it is: Siri
  reads a spoken date in the device's zone.
- **Time zone names.** Found no fault in what devices store or sync. Found
  that setting the time zone returned the name as typed and not as stored,
  two comments that claimed more than the code does, and tests that did not
  check the property older builds depend on. All are corrected. One risk it
  could not confirm is recorded in the roadmap: devices on different system
  versions could hold different names for one zone.
- **Result delivery.** Found no fault in the delivery. Found three existing
  tests that passed whatever the code did once the data was in the text, a
  new test that depended on the system's zone list, and a document that
  claimed the JSON on results that have none. All are corrected.
- **The Today rule.** Found three faults, all fixed before the commit:
  deferring a started task left the change of day out of the record queued
  for sync, the full overview could return no tasks when today's tasks
  filled the top ten, and deferring accepted today or a past day. It also
  found that undoing a review's move of a started task failed when the task
  had gained a blocker since; the undo now leaves that task open.
- **Reminders, repeat start and suggestions.** Found that the apps' repeat
  editors still predicted the start weekday with the old rule, that
  `search_calendar_events` reported a wrong total on a page past the end,
  that a started task planned for a later day appeared in two days'
  suggestions, that the apps could ask for a suggestion with a stale
  today, and that one description promised local time on every reminder.
  All are corrected. It also found three older faults next to the change.
  The plan left in the past is fixed, above. Two are in the roadmap: a
  started task that is hidden until a later day is on Today and also filed
  under Scheduled, and the Shortcuts action names a picked date in the
  device's zone.

No screens were captured for this build. The changes are to which tasks a
list holds, to defaults and to messages; no layout changed.

Not exercised by automation:

- Two devices over iCloud. The tests of the deferral that pauses a task
  check the record one device queues; nothing ran against CloudKit.
- A real assistant client. The seven requests ran through a command-line
  wrapper around the development host, not through an MCP client. Which
  part of a result a client forwards was measured on one client, a headless
  Claude Code 2.1.330 run.
- The refusal sentence on screen. Tests check the text in each language; no
  capture shows it in the app.
- A device whose time zone is a fixed offset. With no stored time zone it
  still has no today.

The built metadata was read in what shipped. The iOS app, its Watch app, the
Mac App Store app and the notarized Mac app each carry build 175. The iOS
package and the Mac App Store package each hold 89 actions, every one with a
declared lock policy, as in build 174.
